Problem: The same SQLAlchemy model schema is defined in two separate modules — any column change must be applied in both places, and they can silently drift.

Solution: Extract models.py and database.py into a shared package that both API and Worker import.

  • Leverage: Alembic migrations reference one canonical source
  • Interface shrinks: Worker no longer needs its own Base + engine setup

Problem: Quota enforcement for registered users uses SQL in quota.py; guest quota uses inline Redis in tasks.py; worker refunds quota through raw SQL copy-paste. Three implementations, one concept.

Solution: Create a quota module that abstracts both registered-user (SQL) and guest (Redis) quota, giving API and Worker one interface.

  • Locality: Quota bugs concentrate in one module
  • Leverage: Worker calls refund via the module, not raw SQL
  • Interface shrinks: two adapters (SQL + Redis) behind one seam

Problem: Three LibreOffice-based converters are 95% identical — the interface (input_formats, output_format, convert) is as complex as the implementation. A bug in one is a bug in all three.

Solution: Replace with a single `LibreOfficeConverter` parametrized by `input_formats` and `output_format` — 3 files → 1 file, 156 lines → ~50 lines.

  • Locality: LibreOffice subprocess logic lives once
  • Depth: Interface is 2 properties; implemention handles all 3 conversions
  • Leverage: Adding a 4th LibreOffice conversion is a one-liner registration

  • Locality: Retry logic doesn't interleave with cleanup logic

Problem: ConvertPageInner mixes state management, polling logic, file validation, API calls, and 6 render branches in one 490-line component. Testing requires rendering the full component with the right props.

Solution: Extract conversion state machine (upload → poll → download) into a `useConvert()` hook with an explicit stage enum, keeping the component as a thin renderer.

  • Interface: Hook exposes { stage, error, upload, download, reset } — testable in isolation
  • Locality: Polling timeout logic doesn't interleave with button event handlers
  • Depth: Hook abstracts the conversion lifecycle; view only maps stage to JSX

Top recommendation

Collapse duplicate DB models into one shared module — it’s the highest-leverage change because every other deepening opportunity (quota consolidation, Celery unification, pipeline decomposition) depends on a shared understanding of the data model. Once the database layer is shared, the rest follows naturally.
